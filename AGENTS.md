# AGENTS.md

## Project Map

Huynity — C++23-проект геометрической библиотеки и движка с программным рендерингом.
Реализованы Math и базовая Object Library; Core, Renderer, Runtime, адаптеры и редактор
пока описаны в документации. Их каталоги создаются вместе с реализацией.

```text
Huynity/
├── AGENTS.md                         # карта проекта и правила разработки
├── .clang-format                     # единый стиль C++
├── CMakeLists.txt                    # проект, C++23, подключение компонентов
├── CMakePresets.json                 # Ninja Debug, binaryDir: ${sourceDir}/build
├── engine/
│   ├── math/                         # реализовано: header-only Point/Vector 2D и 3D
│   │   └── include/huynity/math/
│   ├── objectlib/                    # реализовано: геометрия, фабрики, операции
│   │   ├── include/huynity/objectlib/
│   │   │   ├── params/               # типизированные описания геометрии
│   │   │   ├── primitives/           # Segment, Line, Ray, Plane, Triangle, Aabb
│   │   │   ├── shapes/               # Sphere, Box, Rectangle, Circle, Disk
│   │   │   ├── collections/          # Polyline, Polygon, TriangleMesh
│   │   │   ├── operations/           # bounds, segments, triangulate, tessellate
│   │   │   └── detail/               # внутренние шаблонные помощники
│   │   ├── src/                      # creation, shapes, collections, operations
│   │   └── tests/                    # модульные тесты и CTest
│   ├── image/                        # план: framebuffer и формат пикселей
│   ├── render_contracts/             # план: снимок, задание и результат кадра
│   ├── core/                         # план: сцена, ObjectId, update, Render Preparation
│   ├── renderer/                     # план: синхронный программный рендеринг
│   └── runtime/                      # план: Orchestrator, фазы и жизненный цикл
├── adapters/
│   ├── renderer_actor/               # план: сообщения, завершения, исполнение
│   └── window/                       # план: системные события и показ кадра
├── apps/editor/                      # план: main и UI
├── tests/integration/                # план: проверки взаимодействия компонентов
├── examples/objectlib/               # работающий самостоятельный пример
└── docs/                             # архитектура, API, UML; diagrams/ — SVG и DOT
```

- Публичные заголовки компонента лежат в `include/huynity/<component>/`, обычные
  внутренние заголовки и реализация — в `src/`. Шаблонные помощники, нужные публичным
  заголовкам, допустимы в `include/.../detail/`; соседние компоненты их напрямую не используют.
- CMake-цели: `huynity_math` / `huynity::math`, `huynity_objectlib` / `huynity::objectlib`,
  `huynity_objectlib_tests`, `huynity_objectlib_example`. У каждого компонента свой CMakeLists.txt.
- Object Library зависит только от Math и STL. Она владеет геометрическими значениями,
  предоставляет синхронные операции и не назначает Scene ObjectId. Сценой владеет Core.
- Типизированный API — `createObject<ObjectType::...>(TypedParams)`, runtime-вход —
  `createObject(ObjectSpec)`. Результаты возвращаются через `std::expected`; тесселяция
  отделена от создания параметрической фигуры. Сохранить эти публичные контракты.
- Общие данные кадра не зависят от Object Library, Core или акторной библиотеки.
  Renderer получает неизменяемый снимок; асинхронность относится к адаптеру Renderer.
  ImageBuffer хранится в Image; оконный слой только показывает готовое изображение.
- Пространства имён компонентов: `huynity::math`, `huynity::objectlib` и аналогичные;
  для адаптеров — `huynity::adapters::<component>`. Имена файлов — `snake_case.h/.cpp`.
- Архитектура: [взаимодействие подсистем](docs/subsystem_interaction.md),
  [ревью](docs/architecture_review.md), [UML Object Library](docs/objectlib_class_diagram.md),
  [контракт фабрики](docs/objectlib_creation_api.md), [реализованный API](docs/objectlib_usage.md).

## Определение каталога сборки

- Учитывай явно выбранный каталог или preset. Текущий preset `ninja` использует
  `${sourceDir}/build`; внешнее дерево сборки также допустимо.
- Перед проверками задай абсолютный `HUYNITY_BUILD_DIR`. В новых shell-вызовах
  задавай его снова или используй установленный абсолютный путь; пути заключай в кавычки.
- Для существующей сборки проверь CMakeCache.txt: CMAKE_HOME_DIRECTORY должен указывать
  на этот репозиторий. Сохраняй generator, тип сборки, toolchain и выбранные опции.
- Не создавай новую сборку только из-за другого имени каталога. Если сборки нет,
  используй каталог выбранного preset или путь, заданный в задаче.

## Setup

- Нужны компилятор и стандартная библиотека с C++23 и std::expected, CMake 3.20+,
  Ninja и clang-format 20. Object Library и её тесты не требуют внешних библиотек.
- Работай из корня репозитория. Новая конфигурация: `cmake --preset ninja`.
  Для существующей сборки сохрани её preset или параметры.
- BUILD_TESTING включает тесты CTest; HUYNITY_BUILD_EXAMPLES — пример использования.
  Обе опции по умолчанию включены. Подключение будущих UI и адаптеров должно быть
  опциональным и не мешать сборке Math / Object Library.

## Build & test

```sh
# Для текущего preset; при явно выбранном другом дереве подставь его путь.
HUYNITY_BUILD_DIR="$PWD/build"
cmake --build "$HUYNITY_BUILD_DIR" --parallel
ctest --test-dir "$HUYNITY_BUILD_DIR" --output-on-failure
```

- Для сборки только библиотеки: `cmake --build "$HUYNITY_BUILD_DIR" --target huynity_objectlib`.
- Список тестов: `ctest --test-dir "$HUYNITY_BUILD_DIR" -N`.
  Конкретная группа: `ctest --test-dir "$HUYNITY_BUILD_DIR" -R '^objectlib.creation$' --output-on-failure`.
- Восемь групп тестов находятся в engine/objectlib/tests; это собственный executable,
  запускаемый CTest. Независимые проверки используют площади, объём, владение данными
  и геометрические инварианты. Для новых реализаций добавляй проверки поведения.
- После изменения C++ выполни сборку и связанные тесты; после изменения общих
  заголовков — полный текущий набор. Для документации проверь ссылки, Markdown и diff.
- Сообщай фактический каталог сборки и результаты; незапущенная или прерванная
  проверка не является успешной. Недоступность санитайзеров описывай отдельно.

## Style & conventions

### Именование

- Имена составляй из английских слов и печатаемых символов стандартной клавиатуры. Аббревиатуры нежелательны; если они нужны, выбирай понятные разработчику вне предметной области или добавляй расшифровку в комментарии.
- Новые переменные, параметры, функции и методы — `camelCase`; классы, структуры, перечисления, концепты, алиасы и типовые параметры шаблонов — `PascalCase` (CamelCase с заглавной буквы), без `_`. Нетиповые параметры шаблонов — `camelCase`: `template<ObjectType kind>`. Пространства имён — `snake_case`: `huynity::objectlib`. Сохраняй необходимые соглашения существующих API.
- Выбирай простые осмысленные имена: `midpointCache`, `allowedDeviation`, `frameResult`; односимвольные имена допустимы только в небольшой области видимости, видимой без прокрутки. Чем шире область видимости, тем содержательнее имя.
- В именах переменных избегай `_`, кроме установленного префикса приватных полей. Для логических переменных используй смысловые префиксы `is`, `has`, `was` или аналогичные.
- Приватные и защищённые поля — `m_camelCase`, включая `m_isActive`; публичные поля — без `m_`. Геттеры именуй без `get` (`radius()` для `m_radius`); `get` допустим для метода, который подготавливает результат. Сеттеры — с `set`: `setAlias`.
- Имя описывает фактическое действие: `sampleCircle`, `validateRadius`. Название параметра согласуй с его поведением и документацией.
- Не добавляй венгерские префиксы для обозначения типа. Принадлежность к компоненту выражай через namespace; используй осмысленные имена геометрических типов.
- Глобальные константы — `UPPER_SNAKE_CASE`; константы уровня модуля, функции и метода — `camelCase`. Используй `enum class` со значениями PascalCase, например `ObjectType::Sphere3`.

### Форматирование

- Используй clang-format 20 и `.clang-format` текущего репозитория с `-style=file`: четыре пробела, без табов, ширина 120, `Type*` и `Type&`, без отступа внутри namespace. Не копируй конфигурацию из соседнего проекта.
- Тела `if`/`else`, циклов и веток `case` всегда оборачивай в `{}`, даже для одной инструкции; `switch` также оформляй со скобками. Раскладку скобок и переносов задаёт форматтер.
- Не ставь `;` после определения функции и не оставляй лишние `;;`; после объявления класса или структуры `;` необходима.
- Отделяй логические блоки одной пустой строкой, удаляй хвостовые пробелы, завершай файл переводом строки. Не отступай перед директивами препроцессора.
- В многострочных enum и списках агрегатной инициализации добавляй завершающую запятую, где она допустима и помогает читаемости.
- Перед отправкой кода форматируй все изменённые и добавленные C++-файлы целиком проектным clang-format. Не форматируй посторонние файлы. Если участок требует исключения, используй парные `// clang-format off` и `// clang-format on`.

### Типы, auto и const

- Используй `auto`, когда тип очевиден из правой части; явный тип оставляй для понятности интерфейса, размерности или значения. Нулевой указатель записывай как `nullptr`.
- Неизменяемые локальные значения объявляй `const`; не добавляй его к изменяемым или перемещаемым объектам. Для сырых указателей явно пиши `auto*`/`const auto*` с нужной изменяемостью данных.
- Для чтения элементов контейнера используй `const auto&`, для изменения или перемещения — `auto&`, если нужна ссылка. В цикле по lvalue не применяй `auto&&` без причины, связанной с универсальными ссылками.
- Для константного итератора используй `cbegin()`/`cend()`; для пар ключ/значение применяй осмысленные имена через structured binding, когда это улучшает запись.
- Алиасы объявляй через `using`, не `typedef`; не дублируй их и не добавляй шаблонные параметры без необходимости. Для заданной разрядности используй фиксированные целочисленные типы по правилам проекта.
- Используй подходящее приведение C++ вместо C-style cast; убирай ненужные приведения только после проверки смысла и разрешения перегрузок.
- Не переноси `const` механически между параметрами по значению, ссылками и указателями: учитывай защищаемые данные и различие объявления и определения функции.
- Предпочитай иммутабельный код и `const auto`; сохраняй неизменяемость возвращаемых данных подходящим типом интерфейса. Где возможно вычисление во время компиляции, используй `constexpr` вместо `const`.

### Выражения и константы

- Условия пиши как понятную последовательность проверок; избегай вложенных тернарных операторов и отрицания большого выражения со смесью `&&` и `||`.
- Сокращай лишнюю вложенность ранним выходом; сложную проверку можно выделить в названную функцию или лямбду, разбор enum — в `switch`. Сохраняй короткое замыкание, накопление ошибок, побочные эффекты и время жизни объектов.
- Допустимы прямой возврат выражения, `return {}`, `value_or(...)` и инициализатор в `if`, если это понятнее и сохраняет типы и поведение.
- Магические числа для кодов, режимов и границ заменяй существующим enum или именованной константой. Для значений времени компиляции предпочитай `constexpr` вместо `#define`; не превращай каждую константу в параметр конфигурации.
- Тип строковой константы выбирай по API: не навязывай `std::string_view`, если ожидается `const char*`. Одинаковые операции записи в контейнер оформляй одинаково, проверяя поведение при выборе `emplace_back` или `push_back`.
- Объявляй каждую переменную отдельно, не несколько в одной строке. Избегай выражений с несколькими изменениями одной переменной и неочевидным порядком вычисления, например `i = ++i + --i`.
- Избегай новых макросов; используй возможности языка, константы и функции.

### Классы и инициализация

- В переопределении пиши `override` без избыточного `virtual`; действительно дефолтный конструктор или деструктор оформляй через `= default`, сохраняя свойства типа.
- Независимые от параметров значения полей можно задавать при объявлении. Список инициализации согласуй с порядком объявления полей; порядок параметров конструктора — с ними, если интерфейс допускает изменение.
- Короткую очевидную реализацию допустимо оставить inline в заголовке. Не переноси существующие методы только ради этого предпочтения.
- Для нескольких однотипных аргументов можно рассмотреть структуру параметров и агрегатную инициализацию; переработка интерфейса должна соответствовать задаче.
- Не добавляй ненужное `this->` и не дублируй подряд секции `public`/`private`/`protected`. Имена вроде `previous` или `currentOwnerId` выбирай по смыслу операции.
- В общем случае используй максимум три секции доступа, по одной `public`, `protected`, `private`. Алиасы производных и сложных составных типов размещай в секции по умолчанию до `public`; активно используемые типы из чужого namespace также можно обозначить алиасами. В каждой секции сначала объявляй типы, затем методы, затем поля; статические члены рекомендуются перед нестатическими.
- Для Params и простых данных используй `struct` с агрегатной инициализацией; для геометрических значений с проверяемыми инвариантами — `class` с закрытым состоянием. Методы чтения объявляй `const`.
- Метод, которому не нужен объект, делай статическим; приватный такой метод лучше оформить свободной функцией в анонимном namespace `.cpp`.
- Предпочитай инициализацию объектов через `{}` вместо `()` и `=` с проверкой семантики выбранного конструктора. Значения полей по умолчанию задавай при объявлении; для нуля, пустого значения и нулевого указателя используй `{}` вместо явных `0`, `false`, `""`, `nullptr`.
- Один класс размещай в отдельном файле; исключение — заголовки с логически связанными классами, например примитивами. Файл с классом не должен превышать 1000 строк; превышение требует пересмотра архитектуры.
- Конструкторы с одним параметром объявляй `explicit`. Не вызывай виртуальные методы из конструкторов.

### Функции и параметры

- Функция должна выполнять одно логическое действие, понятное из её имени.
- Рассматривай перегрузки вместо параметров по умолчанию; у виртуальных функций параметры по умолчанию строго запрещены.
- Рассматривай смысловые перечисления вместо параметров `bool`, особенно при нескольких флагах. При большом числе параметров рассматривай структуру данных.
- Простые числовые значения передавай по значению, крупные объекты для чтения — по `const&`. Params фабрики принимаются по значению для передачи владения массивами.
- Неиспользуемые параметры оставляй без имени.

### Владение и стандартная библиотека

- Используй стандартные типы, функции и алгоритмы STL.
- Предпочитай размещение объектов на стеке, когда позволяет время жизни. Использование `new` + `delete` в новом коде требует серьёзного обоснования.
- Для некопируемого объекта предпочитай ссылку сырому указателю, где это подходит интерфейсу. Сырые указатели допустимы для копируемых объектов, когда требуется переназначение связи.
- Перед разыменованием проверяй возвращённые указатели и std::expected, если успех не гарантирован контрактом.
- Избегай Singleton. Если заголовок раскрывает типы, нужные лишь реализации, рассматривай PIMPL для переноса зависимостей в `.cpp`.

### Заголовки и namespace

- Заголовки текущего проекта включай в кавычках, стандартные и внешние библиотеки — в угловых скобках; подключай используемые зависимости напрямую, удаляй лишние и повторные include.
- Заголовки начинай с `#pragma once` вместо include guard. Для типов в сигнатурах методов предпочитай forward declaration, если полное определение не требуется.
- Не добавляй `using namespace` в заголовки. Код размещай в namespace модуля; не повторяй квалификатор доступного имени, если он не нужен для разрешения неоднозначности.
- Хелпер одного `.cpp` можно поместить в анонимный namespace; не выноси его в общий `Utils` только потому, что он вспомогательный. Дополнительные области видимости сохраняй, если они нужны для времени вызова деструкторов.

### Комментарии и документация

- Новые пояснения и документацию пиши по-русски. Нетривиальные методы документируй Doxygen: `@brief`, необходимые `@param` и `@return`; для самоочевидной сигнатуры не добавляй текст ради объёма.
- Объясняй назначение, ограничения, причины, синхронизацию и неочевидные преобразования. Описывай текущее поведение, не пересказывай имя метода, место вызова и ненужные детали внутренних состояний.
- Не дублируй одну ссылку в каждом комментарии. Удаляй закомментированный неиспользуемый код; TODO должен объяснять оставшуюся работу. Документация теста должна соответствовать тому, что проверяется.
- В Markdown используй понятные заголовки и столбцы, прямые ссылки на файлы и поддерживаемые рендерером блоки предупреждений. В описании параметра сначала пиши назначение, затем единицы, ограничения и отключение; избегай разговорных сокращений.

### Проверка оформления

- Форматирование: `clang-format -style=file -i path/to/file.cpp`.
- Проверка: `clang-format -style=file --dry-run --Werror path/to/file.cpp`.
  Используй установленный clang-format версии 20; имя executable может отличаться.
- Для всего текущего C++-кода можно получить список через
  `rg --files engine examples -g '*.h' -g '*.cpp'` и передать его форматтеру.
- Проверь `git diff --check`. Для новых незакоммиченных файлов дополнительно
  проверь хвостовые пробелы и перевод строки в конце файла.
- clang-format задаёт раскладку, но не проверяет именование, владение или инварианты;
  эти требования проверяй отдельно.

## Git & PR

- Сохраняй пользовательские изменения; не включай посторонние файлы и массовое форматирование в diff. Используй принятые соглашения веток и коммитов, не вводи новый шаблон по аналогии с другим проектом.
- Название MR связывай с задачей. Описание пиши по-русски для разработчиков: проблема, итоговое решение, идея и результаты проверок; убирай изменения, которых нет в итоговом diff.
- Перед завершением проверь `git status --short`. Коммит или публикация выполняются по задаче пользователя.

## Security

- Не записывай токены, пароли, закрытые ключи и персональные данные в код, документацию или диагностический вывод. Используй существующие механизмы конфигурации секретов.

## Gotchas

- Object Library содержит синхронные значения и операции. Не добавляй скрытые
  потоки, глобальное хранилище или зависимости на будущие Core / Renderer.
- Примеры в UML сокращены; полный реализованный каталог и численные ограничения
  описаны в docs/objectlib_usage.md и публичных заголовках.
- clang-format не форматирует текст C++ внутри Markdown и не заменяет ревью кода.
- Таймаут или недоступность окружения означают незавершённую проверку, а не успех.

## Task workflow

- **До правок:** прочитай применимый `AGENTS.md`, просмотри пользовательский diff, найди затронутый модуль и тесты; определи каталог сборки по разделу выше, проверь доступность окружения и связанные проверки до изменения поведения.
- **Во время:** выполняй минимальные изменения по задаче; повторяй форматирование, сборку и связанные тесты по мере необходимости, сохраняя внешние API и конфигурационную совместимость.
- **После:** просмотри diff, выполни необходимые проверки из разделов выше, обнови документацию при изменении поведения; сообщи, что изменено, что проверено и какие проверки не удалось выполнить.

## Scope limits

- Не меняй протоколы, алгоритмы, владение объектами, ключи конфигурации или время жизни ресурсов под видом оформления. Расширяй такие изменения только в пределах задачи пользователя.
- Не изменяй посторонние репозитории, настройки CI, зависимости и toolchain без связи с задачей; не публикуй и не развёртывай результат без соответствующего поручения.
- При изменении команд сборки, тестирования или оформления обновляй этот файл в той же задаче. Подробности сверяй с локальными файлами проекта.

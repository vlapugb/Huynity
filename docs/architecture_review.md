# Ревью взаимодействия подсистем Huynity

## Область и вывод

Проверена предложенная архитектура из [subsystem_interaction.md](subsystem_interaction.md)
методами `senior-architect` и `software-design-review`: обязанности → зависимости →
контракты → сценарии отказов. Это ревью проектного решения; исходников и замеров нет.

Базовое разделение пригодно для первой реализации: Core владеет сценой, Object
Library предоставляет обычный C++ API, Renderer получает неизменяемое задание.
Полностью акторная сцена не требуется. Однако предыдущая версия недостаточно
точно описывала транспорт сообщений и жизненный цикл задания. Эти уточнения
внесены в основной документ и отражены в [UML](subsystem_interaction_uml.md).

## Находки по последствиям

| Приоритет | Недостаток предыдущего предложения | Конкретный сценарий | Исправление |
|---|---|---|---|
| Высокий | Нет результата постановки RenderFrame в очередь | Доставка отклонена, а оркестратор уже считает Renderer занятым и ждёт ответ бесконечно | Адаптер предоставляет неблокирующий trySubmit с Accepted / Rejected; Busy наступает только после Accepted |
| Высокий | Не определена проверка корреляции завершений | Позднее или повторное завершение снимает Busy у другого задания | Сравнивать frameId с pendingFrame; несовпадающее завершение не меняет состояние текущего задания |
| Высокий | Требование ждать FrameReady / Stopped не учитывает смерть актора | Исполнитель завершился без ответа; остановка приложения зависает | Отдельный путь RendererDown и подтверждение завершения исполнителя; Stopped ожидается только от живого актора |
| Высокий | У завершений не определены владение и гарантия доставки | Неудачная публикация ответа теряет буфер или оставляет вечный Busy | Канал результата на одно принятое задание; отдельное уведомление смерти; закрытие канала только после остановки производителя |
| Средний | На диаграмме Orchestrator вызывает конкретный UI, но граф зависимостей показывает только UI → Orchestrator | Обработка результата команды вводит обратную зависимость и повторный вход в Core | UI получает результаты через takeResults(); без вызова UI из Core или Renderer |
| Средний | Порядок обработки resize и FrameReady не определён | В одном проходе цикла показывается кадр старого размера, хотя resize уже доступен | Сначала pollEvents и изменение surfaceGeneration, затем обработка завершений |
| Средний | Не выбран шаг симуляции | Скорость мира зависит от частоты главного цикла; длительный кадр провоцирует слишком много обновлений | Фиксированный настраиваемый шаг, ограничение числа догоняющих обновлений за проход, явный учёт отброшенного времени |
| Средний | Синхронная подготовка снимка может быть дорогой | Тесселяция поверхности задерживает UI ещё до отправки Renderer | Сначала измерить prepareFrame; кешировать геометрию по версии, выносить работу в фон только при подтверждённой необходимости |
| Низкий | Framebuffer связан с общим пакетом Render Contracts | Оконный адаптер получает лишнюю зависимость от протокола кадра | При реализации выделить небольшой заголовок ImageBuffer; отдельная библиотека пока необязательна |

Первые четыре пункта — риски корректности будущей реализации. Остальные относятся
к предсказуемости выполнения и сопровождаемости. Они не свидетельствуют о наличии
уже воспроизведённого сбоя.

## Принятые компромиссы

- Один кадр в обработке упрощает владение и ограничивает накопление задержки,
  но не перекрывает подготовку следующего кадра с текущим рендерингом.
- Полный снимок упрощает согласованность по сравнению с дельтами. Его стоимость
  зависит от объёма данных; крупную неизменяемую геометрию можно разделять.
- Render Preparation остаётся внутри Core. Это связывает Core с форматом данных
  кадра, но не с Renderer или акторной библиотекой. При появлении нескольких
  потребителей сцены подготовку можно выделить в отдельный модуль.
- Object Library содержит геометрические операции. Выбор камеры, видимости,
  качества тесселяции и сборка задания относятся к Render Preparation.
- Штатная остановка кооперативная. Если вычисление не завершается, безопасное
  освобождение используемой им памяти по одному таймауту невозможно. Для гарантии
  времени остановки нужны точки отмены внутри алгоритма или изоляция процесса.

## Что проверить при реализации

1. Rejected оставляет состояние Idle, а Accepted порождает один отслеживаемый frameId.
2. Дубликат или чужой FrameReady не освобождает слот текущего задания.
3. RendererDown завершает ожидание даже без FrameFailed и Stopped; память живёт
   до подтверждённого окончания исполнения.
4. Resize, пришедший перед обработкой завершения, делает старый кадр непригодным
   для показа; закрытие окна запрещает отправку следующего кадра.
5. Core продолжает обновляться, пока Renderer читает старый снимок, без изменения
   данных этого снимка.
6. UI забирает CommandResult после фактического apply, с исходным requestId.
7. Большой интервал времени не вызывает неограниченное число update за проход.

Проверки протокола можно выполнить с подставным Renderer, который задерживает,
отклоняет и завершает задания в заданном порядке. Реальный рендеринг для этих
проверок не нужен. Производительность подготовки и растеризации проверяется отдельно.
